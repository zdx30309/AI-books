# 编辑交付可靠性分阶段验收（2026-10-14）

## 每个阶段及发布前的固定检查

1. `git fetch origin`，记录HEAD、origin/main、工作区变更与北京ECS `.deploy-version`。
2. 对线上涉及文件核对Git对应版本的hash；仅文档差异或本轮明确记录的待发布提交可以继续实施。出现未预期业务代码差异必须先合并核对，禁止覆盖协作者部署。
3. 原主目录的四项未提交改动不夹带；仅在已附加干净基线工作树协作，不reset、不force push。
4. 每阶段运行专项离线测试并更新本计划及Epic IMPLEMENTATION_STATUS；发布前重新fetch，确认远端未移动，且无正在生成任务。
5. 发布保留源码/环境/镜像回滚备份；健康、运行文件hash、任务状态和历史付费账本核对后才确认成功。

固定命令：实施阶段运行 `python3 scripts/phase_preflight.py --phase <阶段> --allow-dirty`；提交推送后、发布前去掉`--allow-dirty`。脚本核对已部署Git版本的全部backend/app文件（本轮336份，兼容CRLF），输出阶段记录到忽略的.local/reliability_preflight.jsonl；发现未知源码差异或远端移动直接停止。

## 顺序与验收

1. 审查容量：按完整两稿长度动态分配输出token，上限32768；约25000字离线验证完整输入、预算预留、截断仍阻断、旧凭据不重放。
2. 局部压缩批准：准备稿必须只改第8章、通过篇幅与hash检查；页面显示完整hash，人工确认后事务锁定写批准与恢复，不直接信任客户端文件路径或批准字段。
3. Excel下载：仅Authorization Bearer鉴权Blob下载，校验所有权、文件路径及交付状态，不新增查询串token入口。
4. 人工状态可靠性：暂停、批准、重新生成不能被旧Worker快照覆盖；429重试用尽提示真实，保留明确人工续跑入口，不声称后台永久自动恢复。
5. 标准长文：保留通用短篇18000—22000契约；标准长文11000—25000，离线完整初稿→润色→相似度→降AI→纠错→双Word ZIP；再在新增累计10元预算内真实验收。遇相似度≥50%或费用边界照常暂停，不伪造全链路通过。
6. 完整Word：返回用户原始2026-10-02 Word并对照完整流程；额外朱雀检测PDF/v2/终审等属于旧完整版待启用要求。2026-10-13编辑反馈明确收敛为0.5版（相似度报告＋降AI纠错两Word），与用户此前“先不用管朱雀AI率”一致，不将旧完整版分支擅自混入0.5或增加供应商调用。
7. 发布：每项更新完成/失败/阻塞、命令与测试证据；真实费用为预算核算上界时明确标注，不当实际账单。
